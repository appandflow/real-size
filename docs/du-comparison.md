# How `du` walks a tree, and what real-size took from it

Sources read for this comparison:

- Apple: [`du/du.c`](https://github.com/apple-oss-distributions/file_cmds/blob/main/du/du.c)
  in file_cmds, and [`gen/fts.c`](https://github.com/apple-oss-distributions/Libc/blob/main/gen/fts.c)
  in Libc.
- GNU: [`src/du.c`](https://github.com/coreutils/coreutils/blob/master/src/du.c)
  and [`gl/lib/xfts.c`](https://github.com/coreutils/coreutils/blob/master/gl/lib/xfts.c)
  in coreutils; [`lib/fts.c`](https://github.com/coreutils/gnulib/blob/master/lib/fts.c),
  [`lib/fts-cycle.c`](https://github.com/coreutils/gnulib/blob/master/lib/fts-cycle.c)
  and [`lib/di-set.c`](https://github.com/coreutils/gnulib/blob/master/lib/di-set.c)
  in gnulib.
- Windows: no source is public for `robocopy` or `dir`. Microsoft documents
  `FindFirstFileExW` with `FindExInfoBasic` and `FIND_FIRST_EX_LARGE_FETCH` as
  the faster form of the directory listing both rely on; real-size uses that
  form.

The measurements come from `scripts/bench.mjs` on the CI runners (4 cores,
ext4 root disk, plus 4 GB btrfs and XFS loopback images). Each tool runs 10
times on a warm cache, then once after dropping the caches; the cold figure
is that single run. Two variants of the same code differ by up to 15% from
run to run, so smaller differences are noise.

## What changed

Only the `d_type` skip. It changes no result: the entries it skips were
already stat'ed and then ignored, and they are not counted in `skipped`
either, because they are left out before any call that could fail. The inode sort was implemented, measured
and removed. The benchmark script gained two generated trees for these
measurements: 100,000 files in one directory, and 30,000 symbolic links next
to 300 files.

The remaining gap to `du` comes from what real-size reads that `du` does not:
the APFS private size, the btrfs and XFS extent map of every single-link file
(a 100,000-file directory takes 0.54 s on btrfs against `du`'s 0.11 s on
arm64), and the link count on Windows.
